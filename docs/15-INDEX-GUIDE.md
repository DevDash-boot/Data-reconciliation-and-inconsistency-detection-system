# #15 인덱스 설계 및 EXPLAIN 분석 가이드

이 이슈는 코드가 아니라 **측정과 결정**이 결과물이에요. 인덱스를 먼저 만들지 말고, 측정 → 가설 → 적용 → 재측정 순서로 하세요.

## 순서
1. #12/#13/#14 를 마친 상태에서 PerfRunner 를 100k 이상으로 한 번 돌려 데이터를 남겨요.
2. `scripts/sql/15-index-experiments.sql` 의 **[A] 구간**을 실행하고 결과를 기록해요. (적용 전)
3. **[B] → [C]** 구간을 실행해 인덱스를 추가하고 같은 쿼리를 다시 돌려요. (적용 후)
4. **[D]** 쓰기 비용을 재요. PerfRunner 로 "업로드 적재" 시간이 인덱스 있을 때/없을 때 어떻게 다른지 비교해요.
5. 이득이 있으면 `optional-entities/` 의 `@Index` 변경을 엔티티에 반영하고, 없으면 `[E]` 로 원복해요.
6. 결과를 Wiki 5번(인덱스 설계)과 7번(EXPLAIN 기록), 8번(ADR)에 적어요.

## 미리 생각해 볼 가설 (맞는지 틀린지는 측정으로 확인)
| 가설 | 확인 방법 |
|---|---|
| 로드 쿼리는 (batch_id, 키) 인덱스를 쓰지만 amount, status 를 읽으려고 테이블 본문을 다시 방문한다 | Q1 의 Extra 에 "Using index" 가 없다 |
| 커버링 인덱스를 넣으면 로드가 빨라지지만 INSERT 가 느려진다 | [B] 후 Q1 시간 + [D] 쓰기 시간 |
| 청크 쿼리의 MOD(CRC32(키), 16) 조건은 인덱스로 걸러지지 않고 batch_id 범위 전체를 훑는다 | Q2 의 rows 가 Q1 과 거의 같다 -> 청크 16개면 같은 범위를 16번 훑는다 |
| 불일치 목록은 (job_id, type) 인덱스가 InnoDB 에서 PK(id)를 뒤에 붙이므로 ORDER BY id 에 filesort 가 없다 | Q3 의 Extra 에 "Using filesort" 가 없다 |
| 일별 추이 쿼리는 CAST(created_at AS DATE) 때문에 인덱스를 못 쓴다 | Q7 의 type 이 ALL |

> 세 번째 가설이 맞다면 청크 방식의 다음 개선 아이디어가 나와요: 키 해시를 컬럼으로 저장하고 범위로 조회하기.
> 이건 이 프로젝트 범위를 넘으니 Wiki 회고의 "다음 단계 아이디어" 에 적어두세요.

## 주의
- `ddl-auto: update` 는 **이미 있는 인덱스를 바꾸지 않아요.** 인덱스를 지우거나 바꿀 때는 SQL 로 직접 하세요.
- EXPLAIN 의 rows 는 추정치예요. 시간은 EXPLAIN ANALYZE 로 실제 실행해서 확인하세요.
- MySQL 8.0.18 미만이면 EXPLAIN ANALYZE 가 없어요. 이 프로젝트는 8.4 를 써서 괜찮아요.
